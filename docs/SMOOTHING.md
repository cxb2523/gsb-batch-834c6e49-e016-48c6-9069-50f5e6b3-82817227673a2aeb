# Smoothing: смена кривой, длительности и переиспользование из пула

Документ описывает поведение ноды **Smoothing** (группа *Time*) после исправления
жизненного цикла интерполяции и то, как вручную воспроизвести в браузере сценарий
«переход в процессе → смена кривой → уничтожение → пересоздание из пула».

## Что именно гарантирует процессор

Логика — в `src/components/audio-context/worklet/SmoothingProcessor.ts`.
В контексте процессора, помимо `fromValue / toValue / previewValue / times`,
хранятся `type` (кривая, под которую посчитан текущий прогресс) и `frames`
(длительность, под которую посчитан `times`). На каждом сэмпле:

1. **Смена кривой во время перехода.** Если `props.type` отличается от
   `context.type`, текущий выданный `previewValue` становится новой стартовой
   точкой (`fromValue = previewValue`), `times` сбрасывается в 0, дальше
   до той же цели доходим новой кривой. Стартовое значение не откатывается к
   прежнему `fromValue`, скачка на выходе нет.
2. **Смена длительности во время перехода.** Сохраняется уже пройденная доля
   `progress = times / oldFrames`, затем `times = progress * newFrames`.
   Оставшийся кусок пути доцеливается за новое количество кадров — мгновенного
   перескока нет.
3. **Новое входное значение во время перехода.** `fromValue = previewValue`,
   `toValue = новое значение`, `times = 0` — переход перезапускается от
   последнего реально выданного значения.
4. **Уничтожение и пул.** `CustomAudioWorkletNode.destroy()`
   (`lib/defineWorklet.ts`) кладёт ноду в пул, отправляет процессору `[RESET]`
   (тот воссоздаёт `context` из `initialContext`) и возвращает AudioParam'ы к
   `defaultValue`, а props — к исходным. Повторно созданная нода получает из
   пула тот же экземпляр уже с чистым контекстом: никаких чужих
   `from/to/times`.
5. **Граничные случаи.** При `frames <= 1` или неизвестной кривой
   (`functions[props.type]` отсутствует) — прямой проход `out = value`, без
   исключений; состояние синхронизируется с входом, так что после возврата
   валидной кривой переход снова работает корректно.

Автотесты: `worklet/SmoothingProcessor.test.ts` (поведение процессора, включая
`[RESET]`) и `lib/defineWorklet.test.ts` (пулинг: destroy → повторное создание
тем же экземпляром со сброшенными параметрами и props).

## Ручное воспроизведение в браузере

### Подготовка схемы

```bash
npm install
npm run dev        # открыть выведенный http://localhost:5173
```

1. Добавьте ноду **Slider** (источник сигнала), **Smoothing** (группа *Time*),
   **ShowValue** и **Oscilloscope** (для наглядности), при желании —
   **Destination**, чтобы слышать результат через **Gain**.
2. Соедините сигнальный выход **Slider** со входом `value` ноды **Smoothing**.
3. Выход **Smoothing** подключите к **ShowValue** и на вход **Oscilloscope**.
   Для звука: выход **Smoothing** → вход уровня **Gain** → **Destination**.
4. В ноде **Smoothing** выберите кривую `linear`, выставьте **Frames**
   побольше (например, 4000–8000, чтобы переход тянулся заметно дольше одного
   кадра отрисовки).

### Шаг A. переход в процессе и смена кривой

1. Резко перетащите ползунок **Slider** из одного крайнего положения в другое.
   Число в **ShowValue** и линия на **Oscilloscope** поползут к цели плавно,
   а не прыгнут.
2. Пока переход ещё идёт, переключите в **Smoothing** поле **Type**
   (например, `linear` → `easeInQuad` → `easeOutExpo`).
3. Ожидаемо: кривая на осциллографе меняет форму **с текущей точки без
   разрыва** — нет ни отката к прежнему старому значению, ни вертикального
   скачка. До починки смена кривой пересчитывала уже пройденный путь по новой
   функции, и выход мгновенно прыгал.
4. Повторите тот же приём, меняя **Frames** прямо во время перехода
   (4000 → 500 → 16000). Движение продолжается с той же точки: при уменьшении
   кадров ускоряется, при увеличении — растягивается, но никогда не
   перескакивает вперёд/назад.
5. Снова двиньте **Slider**, не дожидаясь окончания прошлого перехода: новый
   переход стартует от текущего показанного значения, а не от нуля или
   предыдущей цели.

### Шаг B. уничтожение ноды и пересоздание из пула

1. Дождитесь незавершённого перехода (значение на **ShowValue** находится
   где-то посередине) либо просто оставьте **Slider** не в нуле.
2. Нажмите крестик в шапке ноды **Smoothing** — нода удаляется, её
   AudioWorkletNode возвращается в пул и получает `[RESET]`.
3. Добавьте новую ноду **Smoothing** из меню слева. Конструктор сначала
   забирает экземпляр из пула, поэтому с большой вероятностью это будет тот же
   самый worklet.
4. Снова соедините **Slider** → `value`, выход → **ShowValue**.
5. Ожидаемо: новая нода стартует с чистого состояния. Пока **Slider** не
   двигают, выход держится текущего входа без внезапного доворота к чужой
   цели; после движения **Slider** интерполяция начинается с текущего значения
   и идёт полный отрезок по выбранной кривой. До фикса переиспользованный
   экземпляр помнил прежние `fromValue/toValue/times`, и первый же блок
   выдавал рывок или «залипал» на старом значении.

### Как убедиться, что сработал именно пул

В приложении есть отладочная панель **Debug**
(`views/debug/Debug.tsx`), которая показывает счётчики `using` и `created`
из `lib/defineWorklet.ts`: «Worklets: *в использовании* / *создано*».

Быстро удалите и снова добавьте **Smoothing** несколько раз подряд:
знаменатель `created` (число реально созданных AudioWorkletNode) после первого
создания больше не растёт — экземпляры переиспользуются из пула, а каждый из
них при этом ведёт себя как только что инициализированный.

### Проверка граничных случаев руками

- Выставьте **Frames = 1** (или меньше): выход **Smoothing** мгновенно
   повторяет **Slider**, кривая ни на что не влияет, ошибок в консоли нет.
- Программно выбрать неизвестную кривую из обычного UI нельзя, но это покрыто
   автотестом `passes the input straight through for an unknown curve without
   throwing`: процессор не падает и переходит в прямой проход.
